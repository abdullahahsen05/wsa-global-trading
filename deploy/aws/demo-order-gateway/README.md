# Demo-only browser → AWS order pilot

## Platform-wide rollout (October 2026)

The same Lambda now has an opt-in global mode. Its default remains the demo-only pilot above. In global mode, `POST /v1/trade` accepts any connected account for which the web state route minted a signed, account-bound order pass. The order still requires that trader's matching Supabase access token; OPEN requires fresh risk clearance, all actions pass the same zod and worker command validators, and the worker checks ownership and durably reserves `(user, clientRequestId)` before touching the broker. A best-effort per-user limit matches the web route's 30 changes/minute. Any account newly added later is eligible through these checks; no account-id allowlist is needed. A broker response is never guessed or relabeled as executed.

Roll out in this order: (1) deploy the worker code accepting `AWS_WEB_*` audit markers; (2) deploy the Lambda code with `WSA_AWS_ORDER_SCOPE=demo` (the default), add `POST /v1/trade` to its API Gateway integration, and verify that path refuses orders while global mode is off; (3) set Lambda `WSA_AWS_ORDER_SCOPE=all` and `WSA_AWS_ORDER_ENABLED=true`; (4) configure Vercel Production `NEXT_PUBLIC_WSA_AWS_ORDER_SCOPE=all` and `NEXT_PUBLIC_WSA_AWS_ORDER_URL=https://<HTTP API hostname>/v1/trade`, then redeploy. These public values are routing hints, not secrets. `NEXT_PUBLIC_` values are fixed into the browser bundle at build time. Raise API Gateway stage throttling only to a monitored capacity that handles expected active traders; the former demo rate of 2 requests/s is not a platform-wide capacity. The existing standard Vercel route is used when the pass is unavailable, stale, or AWS explicitly refuses before execution. An ambiguous send never falls back to a second execution path.

Emergency rollback: set Lambda `WSA_AWS_ORDER_ENABLED=false`. Every AWS request then returns an explicit pre-send refusal and the browser uses the standard route with the **same request ID**. To remove the shortcut from browser bundles, set Vercel `NEXT_PUBLIC_WSA_AWS_ORDER_SCOPE=demo` and redeploy. This does not disconnect broker accounts or stop copy-trading workers. The browser's route label reads `browser → AWS direct` in global mode; the older demo label remains for the pilot.

The endpoint is still a single-region London worker and provider bridge. It does not guarantee a latency target for every trader location or broker. Before claiming capacity for thousands of *simultaneous* orders, load-test the API rate, Lambda concurrency, worker `WSA_TRADE_DIRECT_MAX_IN_FLIGHT`, Supabase reservations, and API2Trade limits separately. Do not run volume tests with live orders.

This is a temporary, restricted experiment for measuring broker-confirmed WSA Terminal actions without the Vercel function hop. The AWS HTTP API is `10ceux5ih0` in `eu-west-2`, with only `POST /demo/open` (the original path name now carries an action in its body). It is **not** a general trading API. The Lambda `wsa-demo-order-gateway` starts with `WSA_DEMO_ORDER_ENABLED=false` and is limited to the `test1` MetaQuotes-Demo account owned by the test trader. Market opens remain limited to **0.01 lot**; close, partial close, modify, cancel and bulk close on that account may also use the pilot. All other accounts, and pending or larger opens, keep the existing Vercel path.

The browser's last state poll must have issued a signed WSA order pass for the same access token and account. The Lambda checks that pass, the trader allowlist, and the action-specific request schema; a new open also requires the pass's 3-second risk clearance. Risk clearance is not needed to reduce risk by closing or modifying. It signs the existing direct-lane request to the AWS worker, which checks account ownership again and durably reserves `(user, clientRequestId)` before broker execution. Every Terminal action now has an idempotency ID, preserved across an uncertain retry. A possibly delivered request is never retried on another route. A provably unsent request can fall back to the existing Vercel route with the same request ID. The worker writes each confirmed action's `audit_logs` entry in its tracked, retrying write-behind task, using the command ID as the audit ID to prevent duplicate logs. No broker password or worker signing secret reaches the browser.

The account and user IDs are set in Lambda environment, not trusted from the browser. The Lambda holds the London Supabase service key only to validate the existing pass; it must remain a restricted AWS resource. This matches the current Vercel pass key fallback, which uses `SUPABASE_SERVICE_ROLE_KEY` when `WSA_ORDER_PASS_SECRET` is absent. If a dedicated pass key is configured on Vercel later, the Lambda must receive the same key or the pilot will fail closed.

The live site's `NEXT_PUBLIC_WSA_DEMO_ORDER_URL` and `NEXT_PUBLIC_WSA_DEMO_ACCOUNT_ID` only select this one experiment; they are public routing values, not secrets. The AWS HTTP API CORS allows only the WSA Vercel origin, and its stage is throttled. The browser sends a `text/plain` HTTPS POST with no custom headers, putting the same access token, signed pass, and order in the body; this avoids a browser `OPTIONS` preflight. Lambda explicitly checks the WSA Origin and verifies the pass, token binding, account, risk window, and schema before reaching the worker. It does not log the request body. The prior header-based request remains accepted during rollout. An empty simple POST warms the browser and signed worker connections without reserving or placing an order. A successful time report says `Route: browser → AWS demo pilot.` Compare several opens with earlier Vercel-route demo orders from the same device; the first request may still include connection setup or a cold start.

For diagnosis, the API's `$default` stage writes access logs to `/aws/apigateway/wsa-demo-order-gateway-access` with seven-day retention. Only request IDs, method, status, response latency, and integration latency are logged; never log authorization headers, order bodies, IP addresses, or account IDs. CORS exposes `apigw-requestid`, and the Lambda's `Timing-Allow-Origin` exposes Resource Timing only to the WSA site. The terminal report includes that gateway trace ID plus browser DNS, connection (including TLS), and other setup times when the browser provides them. Match the trace ID to an access-log row; `responseLatency - integrationLatency` is gateway overhead, while browser first-byte time also includes network travel and the Lambda's broker-confirmed work. These timing phases overlap and must not be added to the report's residual `network` number.

The pilot accepts an OPEN only while the state poll's signed pass still has over a second of risk clearance remaining; a close, modify, cancel, or bulk close needs over a second of pass lifetime but not risk clearance. The state poll refreshes the risk verdict more frequently for this one demo account, so it does not mint a pass with most of its three-second risk clearance already spent. A near-expiry pass still goes through the standard Vercel route instead of spending a browser round trip on a guaranteed AWS refusal. If AWS explicitly refuses before execution, the panel uses the same request ID on the standard route and reports the refusal and its elapsed time. Lambda logs only a coarse refusal reason (such as `risk_expired` or `token_mismatch`) for diagnosis.

Roll out in order: deploy the backward-compatible worker audit markers first, then the backward-compatible Lambda, then the site. Reversing this order would let a new browser action reach an old worker that does not recognize its audit marker.

Build the AWS Lambda package from the repo root:

```powershell
npx esbuild deploy/aws/demo-order-gateway/index.ts --bundle --platform=node --target=node22 --format=esm --tsconfig=tsconfig.json --outfile=output/demo-order-gateway/index.mjs
Compress-Archive -Path output/demo-order-gateway/index.mjs -DestinationPath output/demo-order-gateway-package.zip -Force
```

Disable the pilot without redeploying the site by setting `WSA_DEMO_ORDER_ENABLED=false` in the Lambda environment. The site will then receive an explicit `notSent` response and use its established Vercel route. Remove the two public Vercel environment variables and redeploy to remove the client-side pilot selection entirely.
