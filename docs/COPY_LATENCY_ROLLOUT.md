# Master-to-follower copy latency rollout

This work targets the time from a master MT5 trade opening to a follower MT5 trade opening. An API2Trade order response is **not** treated as independent MT5 confirmation. No live-money or demo test order is authorized by this document.

## Instrumentation now in the worker

- Each OPEN copy response logs the master broker timestamp (when usable), source detection path (`websocket` or `rest`), event-storage latency, follower preflight, durable reservation, API2Trade session/send time, and response time. Unknown or skewed timestamps are `null`, never zero.
- The API2Trade v1 source counts WebSocket messages, meaningful signals, complete snapshots, ignored frames, resulting events, REST reads/events, and changes first found by the safety poll. An `OK`/heartbeat does not count as an order update in these diagnostics. Set `API2TRADE_STRICT_ORDER_STREAM=true` only for a controlled demo pilot to let a missed order update trigger the existing ten-minute fast-REST safety window even when heartbeats continue; the default leaves the production polling load unchanged.
- Troubled streams log these counters at most once per minute. Set `WSA_COPY_STREAM_DIAGNOSTICS=true` only for a bounded observation window to log healthy streams too; with many accounts this is high-volume. It does not alter execution.
- Run `npx tsx scripts/report-copy-latency.ts --days 7 --limit 500` against an authorized database environment for a read-only broker-synced `trades.opened_at` correlation. It reports match coverage and p50/p95/p99/worst per follower. Incomplete sync or mismatched tickets reduce coverage, not latency. Use a limited time window to avoid large query loads.

The 2026-10-27 read-only seven-day baseline was 20/20 matched links: one follower had 12 samples (p50 1,360 ms, p95 2,750 ms), the other 8 (p50 1,279 ms, p95 2,797 ms). This is a small historical sample, not a post-release measurement or an SLA. The worker's earlier representative trace showed roughly 365 ms source detection, 279 ms event storage, 276–289 ms follower preparation/reservation, and 73/147 ms provider response. Inspect the stage logs after release to see whether those components changed.

## Controlled demo observations, 2026-10-27

The user separately authorized bounded demo-account orders. A 0.01-lot EURUSD master order was copied to one 5%-risk follower at 0.05 lot and both test tickets were closed after each run. A broker-synced master-open to follower-open timestamp is the outcome; provider acknowledgement alone is not counted as MT5 confirmation. Five successful measured runs were **1,536, 2,918, 835, 827 and 906 ms** before risk-spec overlap, followed by **827 ms** with overlap. This tiny, non-random sample is diagnostic only, not a production distribution or latency guarantee. There were no residual test positions or active links for this strategy after the runs; three pre-existing follower positions were not touched.

The first attempted risk-percent copy was skipped because Pro symbol specifications place contract size and tick details inside `symbolInfo`/`symbolGroup`; the adapter only read flat fields. That mapping is fixed. A subsequent successful copy revealed Pro's order response can report MetaTrader integer volume (5,000,000 for 0.05 lot); future copied-link volume is normalized to lots, and a production demo link was verified at 0.05. Historical records were not bulk rewritten.

The v1 Pro `/OnOrderUpdate` stream sent `{ type: "OpenedOrders", data: [...] }` and `{ type: "OrderUpdate", data: ... }` envelopes. The old parser ignored both. The worker now applies the complete opened-orders snapshot and treats an order update as an immediate signal to confirm via REST, while retaining the regular safety poll. A streamed empty list is REST-confirmed before closing a single known position. Before this change, a demo source trade was first noticed at 741 or 2,023 ms; later runs were noticed at about 67–69 ms. These later traces log `detectedBy: "rest"` because the stream signal intentionally triggers a REST confirmation, so that label alone does not mean the stream failed.

The remaining measured hot path is approximately 290–360 ms for durable master-event storage, 280–420 ms for the per-follower reservation, 40–140 ms preflight (cold risk symbol specs are now fetched concurrently with event storage), and about 90–95 ms for the API2Trade order response. The worker-to-database round trip is around 270–300 ms. On 2026-10-27, the Supabase dashboard confirmed that the configured project `platformtrade` (`brtdyxidblyimqteduph`) is in `ap-northeast-2` (Seoul), while the copy worker runs in AWS `eu-west-2` (London). API2Trade v2 event-stream access is not configured on this Pro Basic-auth deployment. No live-money order was placed for these measurements.

## London staging comparison, 2026-10-27

The user approved the additional $10/month project. `platformtrade-london-stage` (`vyuyifegaacqigkzgiws`) was created in `eu-west-2` and remains isolated from production. A logical staging snapshot copied the application schema and data, 12 Auth users and identities, the one empty Storage bucket, and the migration history. The source and staging projects match on 79 application tables, 20 functions, 124 RLS policies, 308 indexes, 49 table triggers, the custom Auth trigger, and 13 Realtime-published tables. All table row counts matched immediately after the copy except `account_snapshots`, `audit_logs`, and `background_jobs`, which continued growing on the live source. The staging API returned HTTP 200 for an anonymous read and the service role returned all 11 trading accounts. No workers or web traffic have been pointed at staging.

A second pass rehearsed the final refresh **only in staging**: truncating the copied application/Auth/bucket rows and loading the same dumps in one transaction with restore triggers disabled. It completed successfully and preserved 12 users/profiles, 11 accounts, 633 master events, 275 copy links, and 13 Realtime tables. A later read-only inventory counted 50 migration records in both projects. The production refresh must use a newly captured dump after writes are paused; reusing this rehearsal dump would lose newer activity.

An isolated London-only Auth smoke test created a temporary email user, signed in with the anonymous client, obtained a session, deleted that user, and verified that the baseline returned to 12 Auth users and 12 profiles. This tests new-project Auth wiring, not migrated users' existing passwords or session continuity.

From an AWS Lambda probe in London, 30 authenticated warm PostgREST reads to the Seoul project measured **p50 264.2 ms, p95 339.1 ms**; 30 equivalent reads to London staging measured **p50 33.3 ms, p95 54.4 ms**. The median network/API saving is roughly **231 ms per database call**. Two serial hot-path writes may therefore save roughly 460 ms, but this is an *inference from read probes*, not an executed trade result. A Seoul-hosted probe saw about 298 ms median to API2Trade's Pro host, versus about 33 ms from London, so moving the worker to Seoul would trade away its fast broker leg. The provider leg and broker confirmation still set a floor; under-100-ms end-to-end execution is not established.

## Isolated London-stage broker-confirmed pilot, 2026-10-27

The user confirmed all candidate accounts are demo and authorized testing without a production database cutover. A temporary copy-worker process ran on the **same London EC2 host** as production, pointed only at the staging project. On staging only, unrelated strategies were paused, and the existing test strategy was temporarily aimed at a connected MetaQuotes-Demo master that production does not follow. The one active follower used risk-percent sizing and was capped at 0.05 lot for this pilot. The production strategies, Supabase URL, and worker services were not changed.

Five 0.01-lot EURUSD demo master trades, each with a stop loss, produced one 0.05-lot follower trade apiece. The independent MT5 broker-open timestamps measured master-to-follower times of **362, 295, 228, 310, and 218 ms**: median **295 ms**, observed range **218–362 ms**. The stage worker's median trace components were approximately 105 ms source detection, 23 ms durable event storage, 40 ms follower preflight, 27 ms reservation, and 97 ms API2Trade response. These trace components are diagnostic, not a replacement for broker-confirmed timing or a guaranteed additive equation. The API2Trade response itself is not independent proof of an MT5 fill.

Each master was closed after its copy was verified. The stage copy engine closed each follower; all five test tickets have exactly one OPEN and one CLOSE event, one CLOSED link with a follower ticket, and no residual test positions. The initial four master and three follower positions were left untouched. The temporary staging worker was stopped, its two temporary AWS SSM parameters were deleted, and staging strategy settings/lot cap were restored. This is a small, non-random comparison with the earlier Seoul runs (which used a different demo master), **not** a production p95/p99 result or proof that every copy will take under 300 ms. The staging data is now deliberately divergent and must be refreshed from a new consistent source dump before any cutover.

## Safe rollout and acceptance

1. Deploy the tracing and stream-detection change to a controlled worker. Keep the existing REST safety poll and durable reservation. Watch the worker for errors, WebSocket discovery rate, duplicate-link conflicts, account reconnection, and broker request failures. If stream load increases, revert the code change rather than silently disabling the safety net.
2. London staging removes most of the observed database round trip while keeping the worker's fast API2Trade leg. Before production cutover, compare complete broker-confirmed copy paths on the same approved demo pair; do not claim the HTTP probe alone as copy-trade latency.
3. For each approved demo master/follower pair, record master broker time, source detection, event store, follower preflight, reservation, provider response, and follower broker-open time. Report p50, p95, p99, worst, coverage, failures, and safety-poll discovery rate. Compare the same account pair before/after each change. No live-money tests.
4. Test duplicate/out-of-order stream frames, stream loss, process restart, risk blocks, all lot-scaling modes, OPEN/MODIFY/CLOSE, and account disconnect. Require zero duplicate orders and no weakened gates.

The API2Trade v2 WebSocket is a separate, **shadow-only demo pilot** if API2Trade confirms entitlement and provides a v2 API key plus account mapping. The current production connection uses a v1 Pro dedicated host with Basic authentication, not a v2 API key. A v2 connection must not replace execution or disable the v1/REST source until completeness and latency have been measured. [API2Trade authentication](https://docs.api2trade.com/docs/authentication) and [v2 WebSocket topics](https://docs.api2trade.com/docs/api-v2/websocket) describe the differing credentials and `positions`/`trades` topics.

## Region move — staging approved, production cutover not performed

A London project requires a new Supabase project and logical migration; a project's region cannot be changed in place, and a project clone retains its original region. The paid staging project is created and the first logical copy is validated. Its source snapshot will become stale as production keeps receiving account snapshots, audit entries, jobs, and trades. Preserve the source project and backups; do not route production to the staging copy as-is.

For a cutover: arrange a master-trading and web-write pause, drain and reconcile outstanding copied orders, take a final consistent copy, verify row counts/permissions/storage/auth, switch web and all workers together, run read-only reconciliation, then resume master trading. `WSA_MAINTENANCE_MODE=true` on a newly deployed web build returns 503 for dynamic page and API requests (including GET handlers with side effects); it is off by default. This web gate does **not** stop already-open clients from writing directly to Supabase, nor does it stop MT5 master activity or AWS workers: the agreed trading pause, worker drain, and source reconciliation are still mandatory. Remove the flag and redeploy after the switch. New-project Auth tokens use a different signing key, so plan for users to sign in again unless session continuity is independently proven. Keep the old project available for rollback until reconciliation is complete. [Supabase region guidance](https://supabase.com/kb/troubleshooting/change-project-region-eWJo5Z) and [migration guidance](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore) apply.

The read-only `npx tsx scripts/check-london-cutover.ts` compares schema inventory, managed Auth/Storage counts, selected application table counts, and pending copy/gateway work. Use `--exact` to count all public tables. **Only after the trading/web pause, worker drain, and final staging refresh**, use `--exact --require-identical` as an acceptance check; it exits nonzero on count differences. It does not establish row-content equality or replace the transactional restore and reconciliation. On 2026-10-27, the source had no pending strategy/self-copy links, copy jobs, or trade commands when checked, but the staging snapshot was stale (including new master events and trades); zero pending at one instant is not approval to switch.

The migration runner no longer hardcodes the Seoul project. It derives the direct database hostname from `NEXT_PUBLIC_SUPABASE_URL`; for a pooler, supply `SUPABASE_DB_HOST` and `SUPABASE_DB_USER=postgres.<project-ref>` so a mismatched tenant is rejected. This is a future-migration safety fix, not a production database change.

Manual Terminal-page direct-lane timing is a separate path and does not measure master-to-follower copying.
